## Trade-off record

These are the places where two goals of the brief pulled in different directions. The record names the side v0.5 chose and the cost accepted. Correctness outranks ergonomics, which outranks performance. Costs marked "unmeasured" have no benchmark yet. The impact map ([Deliverable G]) measures each one in M0, before the item that builds it.

| Conflict | Decision | Cost accepted | Contract |

| Overflow checks against vectorized throughput | Integer and decimal arithmetic is checked everywhere, aggregates and windows included. There is no wrapping mode. | A check on every integer operation and accumulator (unmeasured; M0, before M5). | [§17.1], #221 |
| Deterministic order against parallel scan speed | Readers define file-then-row order, and every terminal restores it with an order-preserving merge. | A merge step, and waiting on a slow partition before later rows can be emitted (unmeasured; M0, before M1). | [§4.1], [§21.1], #148 |

### Rewrites under row-wise demand

[§20.2] fixes which values a terminal demands, and lets an execution evaluate anything else speculatively only if errors from values that are not demanded are suppressed. Once M5 makes integer and decimal arithmetic checked, most numeric expressions can fail, so each DataFusion rule or evaluator that moves an expression onto rows where it is not demanded, or skips rows where a value is demanded, needs a status. The table covers what LTSeq runs at the baseline: DataFusion 55's default rules plus the two Parquet options `src/engine.rs:51-52` turns on, `pushdown_filters` and `reorder_filters`.

- **Safe:** never evaluates a value on a row where it is not demanded and never skips a row where one is.
- **Masked:** safe only if errors of the moved expression are suppressed on rows where it is not demanded, by a selection mask or by carrying errors as values (M16).
- **Restricted:** not applied where an affected value can fail. Masking cannot help, because the skipped rows are never read.

"Probe" means reproduced at the baseline; "source" means read in the crate sources `Cargo.lock` pins. Nothing in the table was benchmarked.

Rows X1–X4 come from the architectural reassessment (P). #273 rated them, with every other rule, in the rule inventory below, and guards every rule it rates Restricted (`src/rewrite_guard.rs`). The subquery decorrelation rules rewrite plans that LTSeq's lowering does not build, and `filter_where`, the one place SQL enters a plan, refuses a subquery. The reassessment found `coalesce`'s short-circuit sound under D10 by reading the source, and pushdown through a union and through a window on its partition keys sound. It also read the `CASE` to `AND`/`OR` rewrite as sound, and a later probe disproved that: DataFusion's `AND` evaluates its right operand on rows its left one already decides, so `CASE WHEN x = 0 THEN false ELSE CAST(s AS INTEGER) > 0 END` became `x != 0 AND CAST(s AS INTEGER) > 0` and raised on a row with `x = 0` that no branch demanded the cast on (R3-F2). The rewrite is now Restricted and guarded by branch demand (`case_rewrites` in the inventory below).

**Early stops in execution.** Two behaviors that skip demanded values belong to DataFusion's operators, not to any rule, so no guard here reaches them. They are M16's evaluation work:

- A hash join whose build side is empty does not read its probe side. `JoinSelection` decides which side is built, but a join that LTSeq plans with an empty left input stops early without any swap.
- A limit stops reading its input once it has its rows. This is the masked case of the `PushDownLimit` row.

`plan_guard_propagate_empty_relation` records the first one.

**Order (X5).** [§9.1] requires every terminal to deliver the defined order. LTSeq reads a sequence of rows in two places, and a rule keeps the order only if it changes neither:

- **The declared order.** A table with `sort_keys` is read through a sort at the plan's root (`LTSeqTable::ordered_df`, #311). `sort` is stable: its last key is each row's position in its input, so rows equal on the declared keys keep their input order.
- **Table order.** A table without a declared order has one only at one partition (`in_table_order`, #148), where `sort` numbers rows, `assume_sorted` collects them and positional operations snapshot them.

Five rules changed one of these. Each is now guarded or turned off, and none is rated as changing the order:

- `EnsureRequirements` met an order requirement on a prefix of a stable sort's keys with a sort by that prefix, which is not stable. Under a window `ORDER BY k` it replaced the stable sort, so `shift(1)` over rows equal on `k` read whichever row came first, even at one partition. Under the root sort it removed the stable sort, after repartitioning a projection that computes a column, so `sort("k").derive(...)` returned ties in any order on several partitions. `ltseq_keep_stable_sorts` fences every stable sort with a node that requires its full order on one partition. `ordered_df` also plans the stable sort itself at the root, above the filters and projections over it (`hoist_stable_sort` in `src/ops/sort.rs`), so no root sort by the declared keys alone is added.
- `join_selection` swapped a hash join's inputs by size, and a hash join returns rows in its probe side's order. It now runs with `join_reordering` off.
- `eliminate_cross_join` rebuilt a tree of inner joins under a filter in another shape. A rewrite that changes a join's inputs is refused.
- `OptimizeAggregateOrder` turned `first_value` ascending into `last_value` descending, which takes the other end of a run of ties. It is turned off.
- `replace_distinct_aggregate` is required: DataFusion plans no `Distinct`. At one partition its grouping returns each group where its first row arrives, and `distinct` declares no order (`set_ops.rs`).

Not covered by any rule: [§9.2]'s order for a table without a declared order on several partitions, and the left input's order for a join, which LTSeq does not claim yet (#148, M1). No rule decides them, as a scan of several partitions returns its rows in arrival order with or without one. `concat_agg` (`string_agg`) concatenates in that arrival order too, while `first` and `last` order by the row number in the group and `top_k` and `mode` by value.

The cost of masking is M0's measurement 4, and its prototype gates M5. Checked arithmetic makes nearly every numeric expression fallible, so M16's masked evaluation has to exist first. Under D10 the measurement covers both operands of a fallible `&` or `|`. The baseline failures in the `AND`/`OR` and merging rows are tracked in #252. M0's m4b priced X4's guard before it merged (#251, `benchmarks/m0/REPORT.md`). Its `keys` placement, a barrier between the operator and its input, is the one `ltseq_keep_demanded_keys` uses. It is taken only where a key can fail, so the m4b pipelines, whose keys cannot fail, keep today's plans.

**`&` and `|`.** The statuses above follow D10 ([Deliverable K]): either operand of `&` guards the other, so the order of conjuncts in one predicate is not observable, while the order of chained filters is. Under the left-to-right rule of `a49af0b`, `reorder_predicates` and pruning on any conjunct but the first would have been restricted, because each can remove the error of a conjunct written first.

### Rule inventory

The table above rates what each kind of rewrite does. This inventory lists every rule that a session created by LTSeq runs, under the name DataFusion gives it. Each rule has a rating for errors ([§20.2]) and one for order ([§9.1]). The guard column names how a rule rated Restricted or Disabled is held to its rating, and the test that asserts its optimized plan.

`src/rule_inventory.rs` holds the inventory to the session. A DataFusion upgrade can add, rename or re-enable a rule, or change one of its rewrites, and each of these fails a test until the rule is rated:

- **Rows against the session.** The rows between the markers below must match the rules of a live session. A rule that runs without a row fails, and so does a row whose rule no longer runs.
- **Ratings.** Every row must have a rating for errors and for order. There is no "not rated" value, and no order rating for a rule that changes the order and runs anyway.
- **Guards.** A rule rated Restricted must run behind the guard its row names:
  - `Guarded`: the logical rule runs wrapped;
  - `GuardedPhysical`: the physical rule runs wrapped;
  - an `ltseq_*` name: that LTSeq rule runs in the session.

  Every wrapped rule must be rated Restricted or Disabled, for errors or for order.
- **Tests.** Every `plan_guard_*` or `test_*` name in the guard column must exist.
- **Version.** The DataFusion version in `Cargo.lock` must be the one the expression rewrites below were rated against.

The check runs in the default build; a measurement build (`m0`) adds its prototypes.

The ratings are those of the table above, plus:

- **Disabled:** LTSeq turns the rule off: by its flag (`keep_unrated_rules_off` in `src/engine.rs`), so a new default does not turn it on, or, for a rule with no flag, by running it wrapped so that it does nothing (`GuardedPhysical`, `Off`).
- **Unreached:** the rule rewrites only a plan shape that LTSeq's lowering never builds, such as a subquery or a grouping set. `filter_where` refuses a subquery (`a_where_clause_with_a_subquery_is_refused`).

**What "fallible" means here.** The guards decide whether an expression can fail with `rewrite_guard::fallible_node`. It is a conservative reading of DataFusion 55's kernels. These count as fallible:

- a cast the program writes that can fail: a `cast()`, or a `CAST`, `::` or `arrow_cast` in `filter_where`'s SQL, each lowered to an `OpaqueCast` (`lower_casts` in `src/ops/aggregation.rs`). A `Cast` that coercion or LTSeq's lowering inserts does not count (`type_coercion` below);
- a division or remainder, unless the divisor is a constant other than 0 and −1, or both operands are floats;
- a pattern match whose pattern is not a literal;
- a subquery;
- any function not known to be total (`TOTAL_FUNCTIONS`).

A constant counts as fallible only if evaluating it fails. Integer `+`, `-` and `*` wrap in DataFusion 55 (X9), so they cannot fail until M5 makes them checked; M5 extends the classifier. The guards are:

- **Logical rules (`Guarded`).** `KeepFailures` counts occurrences, not distinct expressions: two occurrences of one expression are demanded on different rows, so one left elsewhere does not stand in for one a rewrite removes. It accepts a rewrite only if every occurrence of a fallible expression demanded before it is still demanded after it. For `simplify_expressions` the check is on each of the node's own expressions separately, with the occurrences of the expressions the columns it reads are computed from: a simplification may neither drop nor add an occurrence, and where it would, the expression's root is kept and its parts are simplified on their own. `SkipFallible` runs `eliminate_outer_join` only on a filter that cannot fail. `KeepBarriers` refuses a `push_down_filter` rewrite that moves a filter below a `DemandBarrier`. `KeepJoinShape` refuses an `eliminate_cross_join` rewrite that changes the inputs of a join.
- **Physical rules (`GuardedPhysical`).** `NoFailures` runs the rule only on a plan in which no expression can fail. `NoSwap` runs `join_selection` with `join_reordering` off. `Off` does not run the rule.

For order, **Safe** means the rule never changes the sequence of the rows it keeps, in either place LTSeq reads one (X5 above). **Restricted** means it would, and a guard rules the change out. There is no rating for a rule that changes the order and runs anyway. "Reading" in a row means the rating comes from the DataFusion 55 source, not from a probe or a test.

### Expression rewrites

`simplify_expressions` and the physical `PhysicalExprSimplifier` each run many rewrites under one name, and so do the `simplify` hooks of built-in functions. This table rates them by family. A DataFusion upgrade can change a rewrite and keep every rule name, so `src/rule_inventory.rs` also requires the DataFusion version in `Cargo.lock` to be the one in the marker below. All logical rewrites run inside `simplify_expressions`, so its guard (`Guarded`, `KeepFailures` on the node's own expressions) covers every row marked "guarded". The physical simplifier runs inside the Parquet opener, on a scan's predicate and projection, where no rule can wrap it. Its only rewrite that drops anything is the unwrap cast, and it meets no `cast()` the program writes that can fail, as each is an `OpaqueCast`. Line numbers are in DataFusion 55.0.0's sources.
