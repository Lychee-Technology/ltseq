# Changelog

## Unreleased

### Changed

Literal values in lambdas are typed (#145). They used to be sent to the engine as strings and parsed back, so some queries that ran before now raise, and a few return a different result. Expression types now come from DataFusion's coercion as the expression executes (#225). The archived pre-v0.5 reference's ["Literal values" section](docs/archive/pre-v0.5-api.md#literal-values) describes these rules at baseline commit 3041b44.

- An unsupported value in a lambda raises `TypeError` where it is written, instead of being turned into a string: `r.a == [1, 2]` (use `.is_in([...])`), `bytes`, `timedelta`, `datetime.time`, `Fraction`, `complex`. An integer outside Int64, a non-finite `Decimal` or one with more than 38 digits, and `pandas.NaT`/`pandas.NA` raise `ValueError`.
- A string is not a number for a method argument: `shift("1")`, `diff("1")`, `rolling("3")`, `ntile("4")`, `top_k("3")`, `percentile("0.5")` and `dt.add(days="1")` raise `ValueError` naming the method. Pass the number.
- A `Decimal`, `date` or `datetime` compared with a string column raises `ValueError`; it used to be compared as text.
- An aware `datetime` compared with a naive timestamp column raises `ValueError`; the column used to be read as UTC.
- A `datetime` compared with a date column compares instants: `r.d == datetime(2024, 1, 1, 6)` no longer matches 2024-01-01.
- A `date` or `datetime` compared with a numeric column raises `ValueError` when the query is built; it used to fail at collect.
- `fill_null`, `coalesce`, `if_else` and `when` keep DataFusion's common type of their values when every literal fits it exactly, and otherwise give a literal the other values' type when that type holds it exactly:
  - a `Decimal` fill value for an integer column gives a decimal column; it used to fail at collect;
  - one for a decimal column widens the type to keep its digits (`decimal(5, 2)` with `Decimal("1.236")` is `decimal(6, 3)`); it used to be rounded to the column's scale;
  - a `Decimal` that no 38-digit type holds together with the other values raises `ValueError` naming it; it used to be rounded;
  - a float value reads as its binary value under the same rule: `r.i.fill_null(0.0)` on an Int64 column stays Int64 and `r.i.fill_null(1.5)` raises, because Float64 does not hold every Int64; both used to widen the column to Float64, which rounds values past `2**53`. `int32` and narrower columns, which Float64 holds, still give Float64;
  - dates and timestamps work in these positions, an aware `datetime` of another zone as its instant in the column's zone; they used to fail planning;
  - values with no common type raise `ValueError`: a date with a number, a number or Boolean with a date or timestamp column, a `datetime` with a time of day next to a date column (for an aware `datetime`, a time of day in UTC, as comparisons read dates), a `Decimal`/`date`/`datetime` with a string column, and an aware value with a naive column;
  - a string or Boolean literal, and a number next to a string column, keep DataFusion's reading: `r.p.fill_null("1.5")` on `decimal(5, 2)` is `1.50`, and `r.p.fill_null("1.236")` is the rounded `1.24` where `Decimal("1.236")` keeps its digits.
- A number or Boolean next to a date or timestamp column raises `ValueError` when the query is built, in every position: comparisons, `is_in`, arithmetic, `dt.diff` and values. `r.d > 5` on a date column used to compare with 1970-01-06, and `r.ts == True` failed in DataFusion's planner. `dt.add` adds a duration.
- NaN and infinities next to an integer, decimal, date or timestamp column raise `ValueError` when the query is built: `r.i == float("nan")` used to be false on every row, and `r.i.fill_null(float("inf"))` widened the column to Float64.
- `shift(default=)` must be a literal the column holds exactly. `1.5` or `Decimal("1.5")` for an integer column, `-1` for `uint64` and `300` for `int8` raise `ValueError` when the query is built; they used to be truncated, or to fail at collect. A number or Boolean default for a date or timestamp column raises too: `default=5` was 1970-01-06 on a date column and 5 µs past 1970 on a timestamp column. Defaults without an exact rule (a string, a Boolean for a number column) are cast by DataFusion, as before.
- `&` and `|` with `True`/`False` follow the other operand's type (#209). `r.a & True` on an Int64 column raises, as `r.a & r.flag` does; it used to return `r.a`. `r.s & False` on a string column raises; it used to select no rows.
- Expressions without a column are folded by DataFusion, with the types and results it gives the same arithmetic on columns (#193). `LiteralExpr(7) / 2` is the Int64 `3`, as `/` on two Int64 columns is; it used to be `3.5`. `LiteralExpr(2**62) * 4` wraps to `0` like Int64 column arithmetic; it used to be a float.
- Values given to `insert`, `modify` and `update` are literals, encoded and decoded as literals in lambdas are, and written under the rules of `shift(default=)`: the column keeps its type, and a value it cannot hold exactly raises `ValueError` naming the column and the value (#194). They used to be converted by a separate table of their own.
  - A number for a date or timestamp column raises: `insert(0, {"d": 19723})` wrote 2024-01-01, read as days since 1970. Write a `date`.
  - `True` and `False` for an integer or float column raise; they were written as `1` and `0`. A number for a Boolean or string column, and a string for a column of another kind, still raise, now in `modify` too.
  - An integral float or `Decimal` for an integer column is written as the integer (`insert(0, {"i": 2.0})` writes `2`); it used to raise. `1.5` raises.
  - A float for a decimal column is its binary value, as in comparisons: `modify(0, d=9.99)` on `decimal(5, 2)` raises because 9.99 is 9.9900000000000002131…; write `Decimal("9.99")`.
  - A value of a type no literal has (`bytes`, `timedelta`, a list, an expression or lambda given to `update`) raises `TypeError` naming the column, and an `int` outside Int64, `pandas.NaT` and `pandas.NA` raise `ValueError`, before anything executes.
  - A key of `insert` that is not a column raises `ColumnNotFoundError`; the value used to be dropped. `update` raises `ColumnNotFoundError` too, a subclass of the `ValueError` it raised before. The keys are checked before any value, so an unknown key raises `ColumnNotFoundError` even when its value is invalid too.
- `group_ordered(...).first().count()` uses its counting kernel only for predicates the kernel computes as DataFusion does. Predicates with UInt64 order comparisons, Int32/UInt32 or timestamp arithmetic, or a `shift()` with `default=` or `partition_by=` are counted on the general path, which is slower (`docs/BENCHMARK.md`).

### Fixed

- `Decimal` literals compare exactly with decimal and integer columns, also when the comparison would need more than 38 digits: `r.price > Decimal("1.236")` on `decimal(5, 2)` now selects 1.24, and `r.w == 10**18` on `decimal(38, 20)` is false instead of failing at collect (#227). They work in arithmetic with a float column.
- Literals compared with `decimal32`, `decimal64` and `decimal256` columns follow the same rules. A `Decimal` with more digits than a `decimal32` or `decimal64` column holds failed at collect, `decimal256(76, 0) >= Decimal("1.2345")` was true for 1, and an int compared with a negative-scale `decimal64` column panicked.
- `fill_null(1)`, `coalesce` and `if_else` with an integer literal keep a `decimal32` or `decimal64` column's type unless int64 holds every value of it. DataFusion's common type of those decimals and Int64 is int64, which rounded `1.23` to `1`, and failed at collect on `decimal64(18, -1)` values past the int64 range and on `decimal32(9, -1)` values, which Arrow scales up in 32 bits.
- An integer, float or `Decimal` literal compared with a decimal column of negative scale (`decimal128(5, -2)`) no longer panics in DataFusion's simplifier (#226). A fine-scale `Decimal` next to a very coarse column (`Decimal("0E-38")` and `decimal256(76, -14)`, 128 digits together) compares, matches and fills exactly. It used to fail at collect, and `if_else` returned strings.
- A timestamp literal finer than the column's unit was truncated. It now compares exactly in filters, windows, group filters and `is_in` (#200).
- A float literal compares with an integer or decimal column by its exact binary value (#240). `r.x == 2.0**53` on an Int64 column matched `2**53 + 1` too, because the pair compared as floats; `r.p == 0.1` on `decimal(38, 10)` matched `0.1`, because DataFusion rounded the float to `decimal(30, 15)` first. The float `0.1` is not that number, so the comparison is now false; write `Decimal("0.1")` for the decimal.
- `is_in` compares each item the way `==` does, also in a list of mixed kinds: on an Int64 column, `r.x.is_in([2**53 + 1, 0.5])` matched `2**53` too.
- A naive `datetime` in a DST gap or fold, compared with a timezone-aware column, raises `ValueError` naming the zone instead of failing inside the optimizer.
- A `datetime` before 1677 or after 2262 can be compared with timestamp columns.
- `dt.diff` and timestamp subtraction accept `date` and `datetime` literals, and read them as comparisons do: against an aware column, a `date` is local midnight and a naive `datetime` is wall-clock time. `dt.diff` no longer pushes a date against a timestamp through nanoseconds, so dates outside 1677–2262 work there. `-` keeps DataFusion's arithmetic, which subtracts a `date` from a naive timestamp column, or a `datetime` from a date column, at nanoseconds: `r.ts - date(2024, 1, 1)` is a `duration[ns]`, and a date outside that range fails at collect (write a literal of the column's kind, or use `dt.diff`).
- An expression that mixes column types in a CASE (`if_else`, `when`) has the type it executes as. `dt.diff` on an `if_else` of a seconds and a microseconds column reported 10^6 times the elapsed seconds, and an empty result of such a column had the wrong dtype.
- Constant folding keeps integer precision and types: `2**53 + 1` is exact, and `2.0 + 3.0` stays a float (#193).
- `group_ordered(...).first().count()` returns the materialized count for the predicates listed under Changed; the counting kernel used to count some of them differently, for example across `shift(partition_by=)` partitions.
- An unsupported value passed to a method (`r.x.shift(1, default=b"x")`) raises inside the lambda, at the call.
- `shift(default=<expression>)` raises instead of ignoring the default.
- `search_pattern` predicates accept `True`, `False` and `None` literals.
- `modify` wrote nothing, and raised nothing, for a value it could not convert or a column name it did not know: `modify(0, d=Decimal("9.99"))` left a decimal column unchanged (#194, #153 item 2). It now writes the value or raises.
- `insert`, `modify` and `update` write `Decimal`, `date`, `datetime`, `pandas.Timestamp` and `numpy.datetime64` values, into decimal, date, timestamp, unsigned integer and run-end-encoded columns. These raised in `insert` and `update` and were skipped by `modify`; a date column took only a day count.
- A finite float beyond the range of a `float32` column raises `ValueError` as a `shift(default=)` and as a value `insert`, `modify` or `update` writes; `shift(default=1e39)` was an infinity. The range ends at the greatest `float32`, so a value just past it raises too, although rounding would bring it back. A value within the range is still the nearest `float32`.
- `LTSeq.from_arrow` of a struct-typed `ChunkedArray` with a row that is NULL as a whole raises `ValueError` naming the row, as pyarrow's `pa.table` does (#255). The row used to be read as whatever the struct's fields held under it, typically `0` and `""`. To read such a row's fields as NULL, flatten the input first: `LTSeq.from_arrow(pa.Table.from_struct_array(data))`. The refusal applies to every producer: a polars struct `Series` with a NULL row also raises now. polars 2.0 stores NULL fields under such a row, so it was read with those fields NULL; pass `s.struct.unnest()` instead.
- `search_pattern` and `search_pattern_count` combine a step's conditions with `&` and `|` in three-valued logic, as `filter` does (#220). A NULL on either side made the result NULL: `(r.x > 100) | (r.y == 1)` skipped the rows where `x` is NULL and `y` is 1, `~((r.x > 100) & (r.y == 1))` skipped those where `x` is NULL and `y` is not 1, and `(r.y == 1) | None` matched no row. A step can match more rows than before, and fewer only where it applies `is_null()` or `is_not_null()` (`== None`, `!= None`) to an expression that contains `&` or `|`.
- `group_ordered(...).first().count()` evaluates the predicate in three-valued logic when its counting kernel takes it, so the count is the number of rows `first()` returns (#189). The kernel read a NULL left operand of an integer `>` as false when the right operand held one value on every row (a literal, typically), read a NULL operand of an integer `!=` as true, and made `NULL AND FALSE` NULL, which starts a group. With `x = [1, 2, None, 10, 11, 30, 31, 32]`, `(r.x.shift(1) - r.x) > -5` counted 5 groups instead of 7, and `~(r.x != r.x.shift(1))` 1 instead of 3. A count can go up or down. Predicates built only from the leaves of the Parquet fast path (`docs/BENCHMARK.md`, Round 2, condition 3) were already counted this way.
- `group_ordered(...).first().count()` compares floats as DataFusion does when its counting kernel takes the predicate, so `-0.0` equals `0.0` (#244). The kernel ordered Float64 values by IEEE 754 totalOrder, which puts `-0.0` below `0.0`: with `x = [1.0, 2.0, -0.0, 3.0, 0.0, 4.0]`, `r.x.shift(1) == 0.0` counted 2 groups instead of 3, and under `r.x != r.x.shift(1)` a zero that changed sign started a group. A count can go up or down. The predicates affected compare Float64 values, or a difference of two, with `==`, `!=` or `>`, the only float comparisons the kernel takes.
- `is_in` on a float value takes `-0.0` to equal `0.0`, as `==` does, and so do `==` comparisons joined by `|` and the negation of `!=` comparisons joined by `&` (#245). DataFusion compares the items of a float `IN` list bit for bit. It uses such a list for `is_in` with more than three items on a column or two or more on any other expression, and for `==` comparisons of one column with literals joined by `|`, which its optimizer merges into one list once there are more than three: `r.x.is_in([-0.0, 1.0, 2.0, 3.0])`, `(r.x == -0.0) | (r.x == 1.0) | (r.x == 2.0) | (r.x == 3.0)` and `~((r.x != -0.0) & (r.x != 1.0) & (r.x != 2.0) & (r.x != 3.0))` missed the `0.0` rows. The same held for a zero the optimizer computes itself, from the clock (`now().dt.diff(now(), unit="second")`) or from a constant holding an `is_in` (next entry), and for one it writes in place of a derived column that holds it: after `t.derive(z=lambda r: LiteralExpr(-0.0))`, a filter on `r.x.is_in([r.z, 1.0, 2.0, 3.0])` or on `(r.x == r.z) | (r.x == 1.0) | (r.x == 2.0) | (r.x == 3.0)` missed the `0.0` rows. `is_in` also accepts an item that is a column or an expression (`r.x.is_in([r.y, 1.0, 2.0, 3.0])`), which no documentation describes and the v0.5 contract does not admit (#294); it told the zeros apart too, and next to a value of `rand()` it still does (#298). A filter can keep more rows than before, and its negation fewer. A float `is_in` list that holds a zero is also no longer combined with another membership test of the same value by DataFusion's optimizer, which drops NULL results when it does (#296): `r.x.is_in([0.0, 5.0]) & ~r.x.is_in([None, 1.0, 2.0, 3.0])` was true for `0.0` and `5.0` and is now NULL, so such a filter can also keep fewer rows. Lists without a zero are still combined. On a dictionary- or run-end-encoded float column, `==` and `!=` with a zero now treat both zeros alike too; that column's other comparisons still tell the zeros apart (#292).
- A constant that holds an `is_in` (`if_else(LiteralExpr(1).is_in([1]), 2.0**53, 1.0)`) is read as the literal it folds to, as other constants are (#245): next to an Int64 column it compares exactly, so it no longer matches `2**53 + 1`. ltseq counts as constant what DataFusion's constant folding evaluates, apart from stable functions such as `now()`.
- `pivot` compares each value of the `columns` column as a value of that column's own type (#205). It rebuilt each value from its text, so a value that read as a number was compared as one. A string column holding such a value was cast to a number: `["2023", "a"]` failed at collect with a cast error, and `"01"`, `"1"` and `"+1"` each got the rows of all three. A `float32` value that is not a binary fraction, such as `0.1`, matched no row, so its column was all NULL. The `-0.0` rows went to no column, and only the NaNs with the bits of `float("nan")` reached the `NaN` column; both zeros now go to the `0` column and every NaN to the `NaN` column. On a dictionary-encoded float column, `-0.0` also made a `-0` column next to `0`, both holding the `0.0` rows; there is now one `0` column. Other column names and the column order are unchanged.
- `join`, `semi_join`, `anti_join`, `asof_join` and `link` raise `TypeError` for an `on=` lambda that compares a value with `None` using `is` / `is not` (#184). Python evaluated the test instead of capturing it, and a column is never `None`, so `lambda l, r: (r.x is not None) and (l.id == r.id)` joined on `l.id == r.id` alone; `or` and conditional expressions dropped part of the condition the same way. Filter nulls before or after the join with `.is_null()` / `.is_not_null()`. The check cannot tell a column from a Python value, so an `is None` test on a closure value in such a lambda raises too; test it before building the lambda. A test in a helper the lambda calls by name raises as well (#185, next entry). A chained `link` calls its condition when it is created, as `LTSeq.link` does, so an invalid condition raises at the call rather than at the first transform.
- A row lambda (`filter`, `derive`, `select`, `delete`, `update`, ...) or an `on=` condition that calls a helper testing a value with `is None` / `is not None` raises `TypeError` naming the helper (#185). LTSeq rewrites that test only in the lambda's own code; in a helper it is a Python bool, and `or`, `and`, `|` and conditional expressions dropped it without an error: with `def missing(r): return r.b is None`, `filter(lambda r: missing(r) or (r.a > 1))` returned only the rows where `a > 1`. The check follows the helpers a lambda names as a global or closure variable, through further helpers and through `functools.partial`, `lru_cache` and decorators. A function the lambda passes to another one is checked like one it calls, since the code does not say whether the receiver calls it, so `lambda r: use_callback(r, missing)` raises even when `use_callback` never calls `missing`, which used to work. It does not follow a helper called through an attribute (`helpers.missing(r)`, `self.check(r)`) or received as a default value or a `functools.partial` argument, and it skips functions of ltseq, the standard library and installed packages. It reads code without running it, and runs no attribute hook of the objects a helper names, so a lazy or context-bound proxy (werkzeug's `LocalProxy`) is not touched, and a helper behind a forwarding proxy (wrapt's `FunctionWrapper`) is not checked. Helpers are checked, not rewritten, so one that tests a Python value with `is None` raises too: `lambda r: r.a > threshold()` with `def threshold(v=None): return 2 if v is None else v` used to work. Test columns with `.is_null()` / `.is_not_null()`, and Python values against a sentinel object rather than `None`, or before the lambda runs.
- A cast compared with a literal is evaluated, in `filter` as in `derive` and `is_in` (#260). DataFusion compared the column itself whenever the literal fit the column's type, so `r.a.cast("int32") > 5` kept a row with `a = 2**40`, compared unconverted, where `r.a.cast("int32")` alone raises; both now raise. The same rewrite undid a decimal's truncation, so `r.d.cast("int64") == 5` was false for `5.5`, and panicked on a decimal column of negative scale. A cast that keeps every value, such as `int32` to `int64`, is still compared on the column, so Parquet statistics still prune it; a filter on any other cast no longer prunes Parquet row groups.
- `write_csv` and `write_parquet` write to a temporary file in the destination's directory, flush it to disk and rename it over `path` only after the whole table is written, so a failed write leaves a file already at `path` unchanged (#259). They used to truncate `path` first: an unsupported column type, an execution error or a CSV write error left it empty or partly written, and a 0-row `write_parquet`, which raises `ValueError`, deleted it. `write_parquet` of a table read from `path` itself failed after destroying the file; it now works. A symlink at `path` is still followed, also one whose target does not exist yet. What a rename cannot replace is still written directly, and a failed write there can leave part of the output: a device or pipe such as `/dev/stdout` on a terminal or a pipe, a deleted file reached through `/proc/self/fd/N` on Linux, and any `/dev/fd/N` on macOS, so `/dev/stdout` redirected to a file is written in place on macOS and replaced on Linux. A file that is itself a mount point, such as a Docker single-file bind mount (`-v ./out.csv:/data/out.csv`), cannot be renamed over either, but is not written directly: the write fails with `EBUSY` once the whole table is written and leaves the file as it was, where it used to be overwritten. Mount its directory instead. An existing file keeps its permission bits, its group and its ACL (the POSIX ACL on Linux, the extended ACL on macOS), but the file is replaced rather than rewritten: replacing it needs write access to its directory, hard links to the old file keep the old contents, its other extended attributes are not kept, and the new file belongs to the user who wrote it. A writer who is not a member of the old file's group cannot keep that group, and gets a file only its owner can open, since the group bits and the ACL's group entry would otherwise apply to the writer's own group. The flush means a crash leaves the old contents or the new ones, but the rename itself is not flushed, so after a power loss a write that had returned can read as the old file. A process killed during a write leaves a `.ltseq-*.tmp` file behind. On macOS the flush is `F_FULLFSYNC`, with `fsync` as the fallback on a filesystem that refuses it.
- `write_parquet` raises `TypeError` before writing anything when a column is or contains a `struct` without fields or a `fixed_size_binary` of width 0, at any depth of nesting (#259). The first raised `RuntimeError` after truncating `path`. The second panicked in the `parquet` crate with a `PanicException`, which `except Exception` does not catch, or, as a dictionary's values, wrote a file that pyarrow cannot read.
- A sorted table returns its rows in the declared order from every call that reads them, after any filter, derive, window or `group_ordered` step (#311). DataFusion kept a sort's order only up to the next operator it chose to repartition, so on a plan with several partitions (by default one per CPU core, once the input is large enough), `to_arrow`, `to_pandas`, `to_dicts`, iteration, `pa.table(t)`, `show`, `collect` and the writers could return rows out of order while `sort_keys` still reported the sort, and `head`, `tail`, `slice`, `search_first`, `rvs`, `step`, `distinct(key)`, `insert`/`delete`/`modify` by position, `fold` and `asof_join` worked on rows in that wrong order. A `partition_by` or `.over(order_by=...)` window also returned its rows grouped by partition or in window order, at every partition count. Now the declared order is required at the root of every plan that reads rows. A `select` that drops a sort key, or a `derive` that replaces one, still declares only the keys before it, but its own rows keep the input's full order. `select` keeps a key only when it selects the column itself; a computed column that keeps the key's name, such as a cast, no longer does. `collect()` reads back in the order it collected, with or without keys. Rows tied on every key, and the order after a later transform of a table whose keys were dropped, are unspecified. A computed sort key (`sort(lambda r: r.x * 2)`) still declares no order: the rows come back in its order only when read straight after the sort, and after a later transform only the column keys before it are kept. Derive the key as a column and sort by its name to keep its order. Reading a table whose order DataFusion cannot see costs a sort; a plan whose partitions are each in order costs a merge.
- `assume_sorted()` declares its order on the rows in their input order, whatever the table was read from (#148). Only a table read straight from Parquet is declared without reading it; any other (a CSV file or directory, an in-memory table, or a table after a `filter`, `derive`, `union` or other transform, Parquet included) is collected first. On a plan with several partitions it was collected in the order the partitions finished, so the declared order described rows that were not in it: `to_arrow`, the writers, `collect`, `fold` and the other reads could return them out of order at some partition counts and batch sizes, and a `union`'s second input could come first. A table with no declared order is now collected on one partition, which reads each file, row group and batch in order and a `union`'s inputs one after the other, so that collect no longer reads several files in parallel. A table that already has a declared order is still collected in it.
- `group_ordered(...).first()` and `.last()`, also after `NestedTable.filter`, return their rows in group order at any partition count (#196). Their group windows partition the rows by group, and on a plan with several partitions the groups came back in the order the partitions finished, which changed from run to run. The results still declare no `sort_keys`, so a later transform that DataFusion repartitions, such as a computed `derive`, can still reorder their rows, as after a `select` that drops every sort key (#311).
- `head`, `slice` and `search_first` on a Parquet file or directory declared sorted with `assume_sorted()` return the first rows in file order, also after a `filter` (#325). They could skip the first matching rows: on a file sorted by `x` in row groups of 4,096 rows, `t.filter(lambda r: r.x >= 10).head(3)` returned `x = [4096, 4097, 4098]`, and `search_first(lambda r: r.x >= 10)` returned 4096. DataFusion's Parquet reader passed over a row group that the filter matched in part when a later row group that it matched whole held enough rows for the limit. A Parquet source with a declared order is now always read in file and row-group order, which turns that pruning off for it. Without a declared order the reader still prunes this way, so `head(n)` and `search_first` on such a source can return matching rows that are not the first in the file.
- A sort, a window, `search_pattern`, `search_pattern_count` and the `group_ordered(...).first().count()` fast path after a `slice` or `tail` that skips rows work on the slice's rows (#339). DataFusion 55 met an order required after such a slice beneath its offset. After a slice with a length, the sort beneath kept the slice's length without its offset: `sort("date").tail(5).sort("date", "volume")` returned no rows, `sort("g").tail(10).derive(rk=lambda r: rank().over(partition_by=r.g, order_by=r.x))` none of its 10, and on a table with no declared order any sort or window after `slice(k, n)` or `tail(n)` lost rows the same way. After a `slice(k)` without a length of a sorted table, a sort or window in another order ran before the offset and kept the wrong rows, and where nothing after it needed the order, the offset skipped rows in the order they arrived: `len()` and `count()` after a filter, `semi_join` or `anti_join` counted the wrong rows, and `tail()` of such a table returned them. A `slice(k)` without a length of a table with a declared order now numbers its rows in that order and keeps those after the offset, which costs a pass over the sorted rows. On a table with no declared order, a sort after `slice(k)` without a length still runs before the offset and keeps the rows it puts last: which rows such a slice skips is not defined until M1 (#148).
- `partition()` gives each key the rows whose key columns equal it, for every key type (#258). It fetched a partition by writing the key into a SQL `WHERE` clause, so a `date` key read as integer arithmetic (`"k" = 2024-01-03` is 2024 − 1 − 3) and every date partition was empty, also for the dates `read_csv` infers; timestamp, binary, NaN, `time` and `duration` keys, among others, raised `KeyError`, and `map()` raised `RuntimeError` for them. A partition now compares its key as a value of the key column's own type. An aware key is looked up by its instant: the two occurrences of a repeated hour, which Python compares as equal, are two keys, each found by the value `keys()` lists and by its UTC `datetime`, and `map()` keeps both, where it kept one. NaN is one key that any NaN finds and that holds every NaN row, whatever its bits, also on Parquet, where `filter(r.x == float("nan"))` still loses them (#291); `distinct` keeps NaNs of other bits apart (#290), so `keys()` used to list one NaN per bit pattern. Distinct keys that convert to one Python value, such as `time64[ns]` values less than a microsecond apart, which are one `datetime.time`, raise `ValueError` when the keys are first used: `keys()` could list only one of them. `map()` of a `map()` result no longer raises `AttributeError`.
- `derive()` evaluates a `lookup()` only when it is a derived column's whole expression and is called on a column, and its result has no columns but the input's and the derived ones (#223). An expression built on a lookup returned the bare looked-up value without an error: `r.pid.lookup(products, "name") == "ten"`, `.is_null()`, `* r.qty` and `fill_null()` gave the name or the price, and a lookup on a computed key, such as `r.code.s.lower().lookup(...)`, matched the column under it. These raise `ValueError` at the `derive()` call; derive the looked-up value, or the key, as a column of its own and use it in a later `derive()`. Every lookup also added each target column under an internal name, `_lkp_products_name` for a table read from `products.csv` and `_lkp_lookup_table_<id>_name`, which changed between runs, for any other; the result no longer has them. An input column with one of those names made the lookup fail, and a derived column with one came before the columns derived ahead of it; the internal names now differ from every input and derived column. Each lookup now reads its own table on its own key: a second lookup into the same table on another key read the first key's matches, and two tables read from files of the same name, such as `a/products.csv` and `b/products.csv`, were one target, so both lookups read the second. A target read from a file whose name has an uppercase letter or a dot, such as `Products.csv`, no longer fails, and a lookup of a column the target lacks raises `ColumnNotFoundError` naming that column, not an internal one.
